## Резюме

Izzy2 — аккуратный backend-скелет AI Secretary v2 на FastAPI с PostgreSQL/SQLite, approval-flow, Telegram webhook и безопасным значением `EXECUTION_ENABLED=false` по умолчанию. Проект заметно лучше исходного описательного пакета: он содержит запускаемый код, контейнеризацию и базовые тесты.

Production-ready статус пока не подтверждается. До подключения реальных Gmail/Calendar/Telegram-адаптеров необходимо закрыть конкурентную обработку состояний, миграции схемы и безопасный контракт исполнения. Тесты в текущем окружении не запускались: команда `pytest` отсутствует.

## Что сделано хорошо

- Approval token не хранится в открытом виде: хранится hash nonce, токен подписывается HMAC.
- Есть TTL, версия proposal, idempotency key и проверка replay на уровне обычного последовательного сценария.
- Внешнее исполнение отключено по умолчанию; API явно возвращает `501`, когда адаптеры не подключены.
- Telegram webhook проверяет секрет, allowlist владельца и дедуплицирует `update_id` через уникальный внешний идентификатор.
- Контейнер запускается от non-root пользователя, PostgreSQL не публикуется наружу, присутствует healthcheck.
- README честно перечисляет неготовые интеграции и следующие этапы, не маскируя stub под готовый продукт.

## Критичные и важные замечания

### Высокий приоритет — race condition в approve/reject/snooze

`app/services.py:71-129` читает proposal, проверяет `status`/`version`, затем меняет состояние и коммитит без `SELECT ... FOR UPDATE` или атомарного `UPDATE ... WHERE status = ... AND version = ...`.

При двух параллельных запросах оба worker могут увидеть `pending` и один и тот же `version`. Это нарушает гарантию одноразового approval и может создать неконсистентные audit-события. Нужны row-level locking для PostgreSQL, атомарное изменение версии и тест конкурентного сценария.

### Высокий приоритет — `execute_proposal` меняет статус без адаптера

`app/services.py:132-155` при `EXECUTION_ENABLED=true` переводит proposal в `executed` и записывает `adapter_required`, хотя реального внешнего действия нет.

Переключение флага в production может привести к ложному аудиту успешного действия и потере возможности повторного выполнения. До появления конкретного адаптера функция должна оставаться `501`, либо нужен отдельный статус вроде `execution_pending` и transactional outbox с подтверждением результата адаптера.

### Высокий приоритет — отсутствуют миграции

`app/db.py:22` использует `Base.metadata.create_all()` при старте. Это не заменяет Alembic-миграции: изменения колонок, индексов и ограничений на существующей базе не будут безопасно доставлены, а откат схемы отсутствует.

Нужно добавить Alembic, миграции для текущих таблиц и проверку миграций на чистой и существующей базе. `create_all()` следует оставить только для локального тестового режима, если он вообще нужен.

### Средний приоритет — approval API не согласован с описанным Telegram flow

`app/main.py:123-165` все approval endpoints требуют Bearer `API_TOKEN`, а Telegram webhook только принимает сообщение и создаёт `Source`; доставки карточки и callback-контракта нет.

README описывает будущую передачу token в Telegram, но не фиксирует, каким доверенным компонентом будет вызван approval endpoint и как будет защищён callback. До реализации адаптера следует явно разделить внутренний API и публичный callback: отдельная аутентификация, allowlist, rate limit, replay protection и тесты доставки.

### Средний приоритет — слабое покрытие интеграционных рисков

Текущие тесты проверяют HMAC, timezone-aware значение и последовательный single-use approval. Нет тестов FastAPI endpoint-ов, PostgreSQL, Telegram secret/allowlist/replay, конфликтов idempotency, истечения TTL, конкурентного approve/execute, миграций и отказа внешнего адаптера.

Нужно добавить минимальный integration suite с SQLite для быстрых проверок и отдельный CI job с PostgreSQL.

### Средний приоритет — валидация timezone неполная

`TaskCreate.timezone` принимает произвольную строку. `due_at` может быть naive datetime, а база и Pydantic-модель не навязывают единую нормализацию. Это создаёт риск неправильного отображения дедлайнов и DST-ошибок.

Нужно валидировать IANA timezone, явно принимать только timezone-aware `due_at` либо документированно трактовать naive значения через `APP_TIMEZONE`, а в БД хранить UTC с сохранением пользовательской зоны.

### Низкий/средний приоритет — эксплуатационные пробелы

- В репозитории нет CI-конфигурации, линтера и команды автоматической проверки.
- Backup-скрипт создаёт файл, но не проверяет restore и не описывает retention/шифрование.
- `Source.content` и audit payload могут содержать PII; redaction/retention policy не реализованы.
- `docker compose config` без `.env` завершается ошибкой по требуемому `POSTGRES_PASSWORD`; это ожидаемо для production, но quick start стоит дополнить безопасным bootstrap/checklist.

## Проверки

Выполнено:

- просмотр исходников, Compose, Dockerfile, README, тестов и backup script;
- `python -m compileall -q app tests` — успешно;
- `sh -n scripts/backup.sh` — успешно;
- попытка `docker compose config` без `.env` — ожидаемо остановлена требованием `POSTGRES_PASSWORD`;
- попытка `pytest -q` — невозможно в текущем окружении: `pytest: command not found`.

Не проверено: запуск контейнеров, реальная PostgreSQL-интеграция, HTTP smoke tests, restore backup и конкурентные сценарии.

## Рекомендуемый порядок работ

1. Исправить атомарные переходы proposal и добавить конкурентные тесты.
2. Убрать ложный `executed` без подтверждённого адаптера; затем реализовать outbox/worker.
3. Добавить Alembic и CI с тестами на PostgreSQL.
4. Зафиксировать Telegram callback contract и отдельную схему аутентификации.
5. Добавить timezone/PII policy, backup restore rehearsal и operational monitoring.
6. Только после этого подключать Gmail/Calendar write scopes и включать внешнее исполнение.

## Итог

Проект годится как безопасная основа для следующего этапа разработки и ревью архитектуры. Его сильная сторона — честно ограниченный human-in-the-loop каркас. Главный риск — возможность принять конкурентное или «включённое флагом» состояние за фактически выполненное внешнее действие. До устранения этого риска включать `EXECUTION_ENABLED=true` не следует.
